# Qwen3.5-0.8B 三条 Harness 路径：训练与资源评估

评估时间：2026-11-09，服务器 `m20`。依据 [个人 Agent 开发计划](vault-personal-agent-development-plan.zh-CN.md)、[SWE-Agent LLaMA-Factory 使用说明](vault-swe-llamafactory.zh-CN.md)、[三条 Harness 数据状态](vault-harness-data-status.zh-CN.md)、本机短测记录及本次 IPv4 SSH 检查。三个路径均使用 `Qwen/Qwen3.5-0.8B`，固定 revision `2fc06364715b967f1860aea9cf38778875588b17`，独立训练三个 Adapter。历史计划中的旧模型选型已失效。

## 一、判断与边界

**结论：按当前软件与训练配置，现有 8 GiB 显卡无法执行 1024 token 的完整模型合成训练单步；建议把单卡 16 GiB 作为截断或分段后最小流程的待验证起点，单卡 24 GiB 作为较宽裕的工程选型。** 这不是已验证的最低显存：16/24 GiB 都尚未实际训练测试；如果要求保留全部原始长上下文，也不能保证 24 GiB 足够。

三条路径顺序执行，建议至少 8–16 个 CPU 逻辑线程、32 GiB 内存和 100 GiB 可用 SSD；较宽裕建议 16 线程、64 GiB 内存和 200 GiB 可用 SSD。磁盘需求取决于框架镜像与缓存，属于规划值。当前服务器 CPU 和内存充足，但根分区仅剩约 33 GiB。

这里的“跑通”指：数据可转换和审计；模型能完成正反向、参数更新、保存和重载；模型能接入对应真实框架并获得动作执行反馈。**任务成功率、模型能力达到论文水平、以及所有长轨迹无截断都不由资源大小保证。**

### GPU 功能小检查

在服务器独立 LLaMA-Factory 环境中：

- `torch.cuda.is_available()` 返回 `True`；PyTorch CUDA runtime 为 12.4。`nvidia-smi` 显示的 CUDA 12.7 是驱动支持的 CUDA 版本，不是实际 PyTorch runtime。
- Qwen 快照的配置可识别为 `qwen3_5` / `Qwen3_5ForConditionalGeneration`。在当前独立环境内以 NF4、FP16 计算加载完整模型，6 个输入 token、贪心生成 8 个 token 成功；加载模型约 2.397 秒、生成约 0.754 秒，PyTorch 峰值 allocated 821.07 MiB / reserved 868.0 MiB。该单次短输入实测不代表长上下文、微调显存、稳定吞吐或任务效果。
- 加载时提示缺少 fast path 的可选组件，回退到 PyTorch 实现；这个提示本身未阻止短推理，是否影响训练兼容性和速度须实测，不能由此断定需要立即安装额外 CUDA 扩展。
- 一个极小的 `bitsandbytes` NF4 线性层在 FP16 下完成前向和输入梯度反向，结果有限；PyTorch 峰值 allocated 约 8.17 MiB。它只证明这一算子路径可运行，**不证明完整模型能训练、能保存、指定长度能放入显存或得到正常 loss**。
- `torch.cuda.is_bf16_supported()` 默认返回 `True`，但显式 `including_emulation=False` 返回 `False`；因此不要将前者当成 Turing 原生 BF16 支持。当前方案使用 FP16，数值稳定性仍须短测。

### 完整模型训练显存探针（新增，2026-11-09）

使用服务器当前 LLaMA-Factory 0.9.5 加载固定版本的完整 Qwen3.5-0.8B，NF4 双重量化、FP16、LoRA r=8（q_proj/v_proj）、batch 1、梯度检查点。输入为无 padding 的合成 token，32 个目标 token，使用 AdamW 和动态 loss scaling；每项是短暂探针，不是 Trainer 的完整数据训练或保存重载测试。

| 序列长度 | 结果 | PyTorch 峰值 allocated / reserved | 限制 |
|---:|---|---:|---|
| 512 | 第二次尝试成功更新，24 个参数张量改变 | 5,211 / 5,514 MiB | 首次 FP16 梯度非有限，GradScaler 跳过更新并降低 scale；两次尝试合计 2.297 秒。 |
| 768 | 一次更新成功，24 个参数张量改变 | 7,190 / 7,220 MiB | 单次约 1.545 秒，余量很小；不能视作稳定训练步速。 |
| 896 | 前向 OOM | 失败前 6,892 / 7,036 MiB | 需要再分配 850 MiB 时仅剩约 660 MiB。 |
| 1,024 | 前向 OOM，两次复现 | 失败前 6,696 / 6,850 MiB | 需要再分配 970 MiB 时仅剩约 872 MiB。 |

探针启动时 PyTorch 看到总容量约 7,789 MiB、空闲约 7,606 MiB；数据导出进程当时占约 90 MiB。结果只适用于此版本和配置，不代表 8 GiB 在所有优化下都不可能训练 1,024。单独隔离测试 Liger 0.8.5 的 1,024 路径时，前向报 `Internal Triton PTX codegen error`，未完成更新；原因尚未定位，不能将其视为已验证的节省显存方案。服务器临时日志为 `/tmp/vault-qwen35-lf-probe-{512-v2,768,896-v3,1024-v3,1024-liger-085}.log`，临时目录可能被清理。

当前 Transformers 损失实现会将 logits 转为 FP32。若某实现完整物化 batch 1 的 `[序列长度, 248320]` FP32 logits，单个张量在 1,024 / 8,192 / 32,768 token 时约占 0.95 / 7.58 / 30.31 GiB；这只是形状计算，不是 GPU 总需求或对 OOM 的确定归因。融合损失、分块等实现可能避免这一完整张量，模型权重、激活和其他开销则另计，因此无法从此公式直接推断最低显存。

## 五、三条路径的最小训练方案

按 SWE-Agent → OpenHands → AgentLab 顺序，各自使用相同只读基座独立训练：

1. **数据与接口：**每路固定框架版本、工具/动作定义、训练输出格式及模型模板；从各自训练候选先选 20–50 条有代表性的已审计轨迹做流程验证，保留独立验证和测试任务。20–50 是初始抽样建议，不是效果保证。
2. **转换及数据检查：**原数据 → ADP → 目标框架 SFT → Qwen3.5 样本；保存来源、split、排除及截断报告，检查 system、任务、反馈、目标和 loss 标签。SWE 路径先检查已完成导出的报告；OpenHands 与 AgentLab 尚需实现或核实各自的转换和真实接口。
3. **基座基线：**在相同模型提示模板、工具、任务和生成参数下运行框架，记录可解析率、工具成功率、任务结果及失败案例。真实交互所需的 SWE-Agent / OpenHands 沙箱、AgentLab / BrowserGym 网页环境应按各自版本配置；SFT 阶段读取已有轨迹，不需启动它们。
4. **训练短测：**每路在不影响其他进程的情况下使用 batch 1、4-bit NF4、FP16、LoRA 和梯度检查点；先在有足够显存的环境按 1,024、2,048、4,096 逐级测试真实样本，再做 10 个优化器步骤，检查有限 loss、显存峰值、实际更新、保存和重载。OOM 时降低长度或调整方案并重新导出，不覆盖已有结果。
5. **扩大与对照：**短测成功后在真实长度分布上测至少几十步，依据有效样本数选择训练轮数与检查点；分别生成三份 Adapter。在相同独立任务上比较每个基座与对应 Adapter，记录任务成功及普通对话回归。方案确定后再使用测试集做最终评估。

当前 SWE-Agent 的 LLaMA-Factory 路径支持 `--eval-steps`、`--save-steps` 配置，但服务器的定期验证、恢复、Adapter 重载和模型训练均未实测。旧本机模型服务的提示模板与新训练模板有差异；评测前须逐 token 对齐动作前缀并重新跑基座。初期评测以受控小仓库和本地网页为主，不能把离线 loss 或 XML 解析率当作任务成功率。

|---|---|---|
| RTX 3050 Laptop 4 GiB，SWE 真实来源，256 token，旧 PEFT 脚本 | 90 步 59.489 秒，约 0.661 秒/步 | 只反复使用 9 条、全部左截断的样本；不是服务器、不是 LLaMA-Factory，也不能衡量模型泛化。 |
| 同卡，512 补齐合成样本 | 3 步 4.243 秒，约 1.414 秒/步 | 合成数据和大量 padding，样本非常少。 |
| 同卡，768 补齐合成样本 | 5 步 13.686 秒，约 2.737 秒/步 | 有效输入约 278–279 token，不能代表真实 768 / 1024 / 2048 长度。 |

这些数字不能直接推算 2060 SUPER 或三个 Harness 的速度。使用它们仅作对时间量级的敏感性分析：假设**每路有 1,000 个有效决策、训练 2 个 epoch、batch 1、梯度累积 1，全部样本各用一次**，每路约 2,000 个优化器步骤；在假设速度为 0.661、1.414 或 2.737 秒/步时，纯训练循环分别约 **22、47、91 分钟/路**。这是数学外推，不是 2060 SUPER 的实测速度，也不适用于假定的 1024/2048 token；三路若恰好都满足相同假设，纯训练循环合计约 66、141、273 分钟。实际三路输入长度、数据量和有效样本不同。

另一种不依赖旧硬件的情景：仍以每路 2,000 步为例，如果实际平均为 1 秒/步、3 秒/步或 5 秒/步，纯训练循环分别是约 **33 分 20 秒、1 小时 40 分、2 小时 46 分 40 秒/路**；三路顺序合计约 **1 小时 40 分、5 小时、8 小时 20 分**。这些只是明确给定步速的算术例子，不是对该 GPU 的性能预测。

预计总耗时还包括模型加载、数据转换和审核、tokenization、训练框架预处理与 `audit`、验证、保存和重载、框架环境构建、基座与 Adapter 多任务评测及失败重试。当前 SWE 导出已耗费数十分钟 CPU 工作，不能忽略；其他两路预处理时间也未测。

### 服务器上如何得到可复核预测

每条路径分别记录，并把报告、日志和固定配置放到对应实验目录：

1. 从最终 `report.json` 记录有效训练样本 `N`、验证样本、原始与截断长度分布、排除比例和训练数据哈希；记录 batch、梯度累积 `G`、epoch `E`、实际最大 token 和随机种子。
2. 在真实数据、目标长度和同一 GPU 配置下，先验证 10 步能完成。再进行至少 50–100 个优化器步骤的计时短测，单独标注模型加载、数据预处理、训练、验证和保存时间；避免只用首步或合成填充速度。
3. 单 GPU、每设备 batch 为 `B` 且不丢弃样本时，近似每个 epoch 的优化器步骤为 `ceil(ceil(N / B) / G)`；乘以 `E` 得预估步数。具体以训练器对最后不完整 batch、梯度累积及 `max_steps` 的实际行为为准。
4. 用同配置短测的训练循环平均秒/优化器步乘目标步数；梯度累积增大时每个优化器步包含更多前反向，不能沿用 `G=1` 的秒/步。可结合训练日志 `train_runtime`、实际步数、样本数和 GPU 峰值交叉核算，并加上实测的加载、验证、保存和评测耗时。
5. 若样本长度差异大，按短/中/长真实样本分层记录速度和占比；或使用与正式数据同分布的短测。报告估算范围与失败风险，不根据单条样本承诺总时长。

第一次 10 步属于兼容性验证，得出稳定用时前不扩大长训练。训练时间与数据导出时间分开记录。所有结果需标注显卡、驱动、软件版本、模型 revision、数据和配置哈希、GPU 空闲显存及观察时间。
