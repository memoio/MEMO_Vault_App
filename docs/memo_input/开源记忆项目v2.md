### 2.2 MEMO Vault 的评价边界

本报告以用户给定的目标为准：原始数据导入与归档、候选记忆、用户确认、来源证明、授权读取、撤销和 Memory Pack 迁移。**本次未获得 `vault-memory/1` 的正式 schema**，因此所有映射建议都是概念和适配器设计建议，不是已验证的格式兼容结论，也不是对正式字段名的臆造。

下文使用三个标签：

- **项目事实**：可在所列官方证据中定位的现有结构或行为。
- **Vault 判断**：基于项目事实对本 MVP 的适配性、风险和边界判断。
- **验证要求**：落地前应补做的实验；未执行的实验不写成已经通过。

### 2.3 推荐结论

**建议将 mcp-memory-service 列为“可替换的本地检索/记忆处理后端”的首选 PoC；将 Basic Memory 列为“平台导入、Markdown 知识表示与上下文导出”的重点参考及备选兼容后端。两者均不应直接充当 MEMO Vault 的最终事实库。**

这是架构与集成成本判断，不是检索质量排名。推荐前者的主要依据是 Apache-2.0、现成 MCP/REST/Python 接口、存储抽象和本地路径；不是因为它已经满足来源证明、人工确认或细粒度授权。其全局去重、自动演化/合并、插件异常继续等行为还需要适配限制。

Basic Memory 在聊天导入、可读文件与图谱上下文方面更贴合“用户可迁移资产”的体验，但其聊天导入是有损转换；而 AGPL 对直接嵌入、修改并运营闭源产品的路线构成需要先解决的许可条件。若 MEMO Vault 自身采用兼容开源许可，或获得明确适用的其他授权，Basic Memory 的候选优先级应重新评估。

## 三、mcp-memory-service：十维度深入核查

### 3.1 主流模型数据导入

**项目事实：如何实现**

1. 文档摄取以 `DocumentLoader` 为基础，通过注册表按扩展名/MIME 选择加载器。注册表列出 Markdown、TXT、JSON、CSV、PDF 等，部分 Office 格式依赖额外工具。文件被解析为 `DocumentChunk` 后写入记忆。[M03][M10][M22]
2. `JSONLoader` 的主要语义是把对象/数组递归展开为带键路径的文本，然后分块；默认策略可产生 `mapping.<node>.message...` 一类文本。它没有在此路径实现 ChatGPT 会话分支、角色、消息证据对象的专用标准化。[M04]
3. `TranscriptParser` 明确支持 Claude Code、Kiro CLI 和 OpenClaw 的特定轨迹格式，解析用户/助手文本，结构中可以带 timestamp、uuid。**Claude Code 本地 JSONL 与 Claude.ai 导出的 conversations.json 不是同一种输入**。[M05]
4. 检查 `ingestion/`、`harvest/`、`sync/` 及相关脚本后，未发现面向 ChatGPT、Claude.ai、Gemini/Google Takeout 导出包的完整专用适配器；未在加载器注册中发现通用 ZIP 历史包入口。同步 JSON 的导入器要求本项目的导出结构，不能被称为“任意 JSON 导入”。[M03][M30]

**Vault 判断**

它适合作为“已有标准化文本/记忆 → 分块与检索”的参考，不能直接解决“主流模型历史 → Vault Message/Evidence”的问题。把 ChatGPT JSON 直接交给通用加载器虽然可能得到可搜索文本，却会把 ID、内容、元数据混为文本；后续很难可靠地恢复分支、附件与逐条证据。

建议 Vault 自己解包并保留原始 ZIP，按平台实现解析器；原始文件和标准化消息先归档，再把经确认的记忆或明确标记的候选发送到后端。若复用轨迹解析器，应把其支持的内容块、工具结果与未提取计数作为显式能力声明。

**验证要求**：分别测试 ChatGPT 分支/多模态、Claude.ai 内容块/附件、Claude Code 工具调用与 Gemini Takeout，检查输入消息数量、跳过原因、时间和 ID 完整率，不能只检查“导入成功”。

### 3.2 记忆存储

**项目事实：如何实现**

默认 `MCP_MEMORY_STORAGE_BACKEND` 为 `sqlite_vec`。`Memory` 数据类包含 `content`、`content_hash`、`tags`、`memory_type`、任意 `metadata`、可选 `embedding`，以及创建/更新时间。SQLite 侧将正文与 metadata 等持久化，向量使用 sqlite-vec，另有全文检索和图关系结构。[M06][M07][M14]

可选后端包含 Cloudflare、hybrid、Milvus；它们并不天然具有完全相同的 metadata、事务或同步约束。Cloudflare/hybrid 不是“完全本地”的别名。基础存储接口为 `MemoryStorage`，业务层由 MemoryService 统一调用。[M19][M26]

值得注意：SQLite `memories.content_hash` 是全局唯一列；写入前按 `content_hash` 查重，没有在该查询中加入 store。hash 由正文去首尾空白并转小写后计算，不包含 owner、store 或来源。当前虽有 store 分区，不能假设相同内容可在两个 store 中独立存成两条记录。[M07][M31][M34]

**Vault 判断**

它的记录形态便于承接“记忆正文 + 类型 + 可扩展元数据”，但任意 metadata 只是扩展容器，不提供正式 schema 校验、证据约束或用户确认语义。不要把内容哈希直接当 Vault 的稳定 Memory ID：正文修改会改变内容身份；不同用户的相同内容也不能被全局合并。

推荐保留 Vault 独立 ID 与版本，维护 `Vault ID ↔ 后端 hash/分块 ID` 对照。向量、全文、图关系作为可重建投影；原始证据和确认记录由 Vault 管理。多用户 PoC 优先使用独立实例/数据库隔离，而不是假定共享 SQLite 的 store 已足够。

**验证要求**：同文不同用户、同文不同证据、同一记忆改写、长文本自动分块和重建索引；验证各后端嵌套 metadata 的往返与 hash 映射，禁止默默丢字段。

### 3.3 记忆形成

**项目事实：如何实现**

它存在多条不同的写入/处理路径：直接 store；文档分块；会话 harvest；实时 auto-capture；质量评价和 consolidation。harvest 候选模型记录正文、类型、标签、confidence、source_line、抽取方法和模型；`HarvestConfig` 默认 `dry_run=True`、`use_llm=False`。[M08][M24]

规则抽取依赖 locale patterns；本次快照可见英文、德文和巴西葡萄牙语规则文件，不能据此承诺中文抽取效果。可选 LLM provider 做分类或重写；重写提示词偏向编码场景的长期决策、修复和习惯，并主动过滤临时事实和部分元讨论，未必适合个人生活记忆。[M17][M32]

consolidation 可涉及衰减、聚类、关联、压缩、遗忘等；总开关默认关闭，但内部子能力存在各自默认值。harvest 在非 dry-run 时可以直接写入或演化已有记忆。质量分数和语义去重不代表事实已被用户确认。[M09][M20]

**Vault 判断**

这是两者中更值得验证的“处理层”，但应将引擎输出视为候选。`dry_run` 只是运行模式，不是持久化审核队列：它没有自动提供“谁在何时确认了哪个版本”的证据。拒绝、修订、撤销也不能靠 confidence 表示。

Vault 应在后端之外实现审核状态机，只将已生效版本提供给 Gateway。禁止自动合并或遗忘直接改变 Vault 主记录；这些动作应回传为建议/事件。中文和非编程个人记忆需要另建样本，不能直接继承英文规则的可用性结论。

**验证要求**：同一来源重复抽取、互相矛盾的陈述、否定句、用户更正、时效性偏好，以及候选未确认时的检索隔离。比较规则与指定本地 LLM 的精确率和漏提率。

### 3.4 来源可追溯性

**项目事实：如何实现**

文档加载基础 metadata 包含 `source_file`、文件名、扩展名、大小、修改时间、loader 类型；分块对象有来源文件和 chunk index。它是有用的文档来源记录，但路径和修改时间不能证明文件内容一直未变。[M10][M22]

harvest 的持久化 provenance 包括 `harvest_session_id`、`harvest_method`、`harvest_model`、`harvest_pipeline_version` 和 confidence。候选结构另有 `source_line`，但 `_provenance()` 构造的 metadata 没有自动复制该字段，也没有强制记录原始消息 UUID、精确字符区间或原文哈希。[M08][M09]

部分接口接受 `conversation_id`，会话存储也可以记录上下文，但“调用者可以传入会话 ID”与“每条记忆必有经过验证的证据引用”是两种能力。[M13]

**Vault 判断**

评价应为“有来源元数据基础，证据链不完整”，不能写成“完全不可追溯”，也不能写成“支持来源字段所以已满足 Vault”。尤其 `source_line` 名字不是行号；它承载的是触发抽取的原始文本，若没有进入持久化结构，候选入库后该信息可能丢失。

Vault 应保存不可变原始对象、平台/会话/消息标识、消息时间、分支和附件关系，以及证据片段的定位与校验；记忆引用这些证据，后端只保存可关联的 Vault ID。引擎报告的“session coverage / safe_to_delete”只反映它自己的抽取覆盖判断，不能替代归档保留策略或证明所有消息与工具轨迹已经保存。

**验证要求**：从一条已确认记忆回放到原始字节及片段；移动/修改原文件后仍可定位；多来源归并后每个来源都保留；导出后在空环境重建证据关联。

### 3.5 记忆导出

**项目事实：如何实现**

`MemoryExporter.export_to_json()` 输出导出 metadata 和 memories，记录正文、hash、标签、类型、创建/更新时间、metadata、store、来源机器；可选包含向量，支持标签筛选。当前实现遍历 stores 获取记忆，仓库提供调用它的导出脚本。[M11][M25]

这一路径导出的是记忆记录，不能自动推导其包含所有 graph edges、版本历史、同步事件、删除墓碑、OAuth 授权和原始附件。导出机器标识只是本次导出的来源，不是某条记忆的原始证据来源。

源码还有 `knowledge_export` MCP prompt 的 JSON/Markdown/text 格式化实现，部分路径只取最近 100 条或检索前 100 条；同名工具 handler 又存在引导页委派。不能把它当作统一、无上限、无损的 Markdown 导出契约；MCP prompt 与 MCP tool 也不相同。[M23]

**Vault 判断**

JSON exporter 可作为适配输入，但 Vault Memory Pack 应从 Vault 的主记录构建。必须显式确定导出哪些版本、哪些证据、是否脱敏，以及授权是否允许携带。面向新模型的上下文包需要控制 token、去除无关内部字段，并附上来源引用；数据库备份和上下文包是不同产物。

对于原始来源丢失的数据，导出器不会补回证据。也不应将全部 store 导出器直接暴露给只有单个 namespace 授权的 Agent。

**验证要求**：全量与筛选导出数量核对；嵌套 metadata 和中文往返；原记忆 ID/版本映射；图边与删除记录的独立处理；确认上下文导出不会被默认 100 条上限静默截断。

### 3.6 MCP / API / SDK

**项目事实：如何实现**

仓库提供 MCP 服务、HTTP REST 路由与包内 `mcp_memory_service.api` Python 接口。Python 层公开 search、store、health、consolidate 等封装；HTTP/MCP 通过服务层和存储层访问数据。[M13][M21][M26]

这些是实际存在的集成入口，但并不意味着每个 transport 的所有函数签名、默认分区、过滤、错误或返回结构都完全一致。不能仅凭一个 Python 内部调用成功就判定远程 MCP 权限也成立。

**Vault 判断**

接 Gateway 的可行性较高，MVP 可优先封装 HTTP 或 MCP 的最小只读集合，并固定服务版本与响应适配。Vault 的身份认证、授权撤销、审计和状态过滤必须发生在 Gateway 内，后端只接受 Gateway 身份。

对外部 Agent 不开放后端的管理、全库导出、任意元数据改写和自动清理入口。引擎的写入应进入候选 API，不能直接赋予其生效资格。

**验证要求**：同一查询经选定 transport 的 store/类型/标签过滤一致；分页不漏项；连接超时和重试不重复写入；大结果显式报告截断；MCP 与 REST 的拒绝行为一致。

### 3.7 权限与命名空间

**项目事实：如何实现**

本次源码有 `store` 分区；HTTP 写入默认 `default`，读取可用 `all` 转成无分区过滤。读取、更新、删除等路径带 store 参数。另有 `proj:`、`topic:`、`user:` 等标签分类。[M06][M13]

认证依赖中有 OAuth/JWT、API key 和 read/write/admin scope；API key 获得完整范围。检查的 memories 路由将请求给出的 store 传入存储，没有在该处将请求者身份绑定到允许的 store 集合。这里的 scope 是操作范围，不是命名空间 ACL。[M12][M13]

此外，全局内容哈希唯一与去重逻辑意味着 store 不等于独立租户数据库。跨 store 的同文行为必须单独验证。[M07][M31]

**Vault 判断**

不能把 tags 或 store 解释为用户访问控制。Gateway 必须根据已认证的主体和有效 AccessGrant 在服务端计算 namespace，拒绝 Agent 自报 owner、任意 store 和 `all`；还要覆盖搜索、图遍历、详情、导出、统计和缓存。

对个人单用户原型，store 可以承担组织用途；对多用户服务，优先独立实例隔离，或在彻底审计数据模型及查询后再使用共享库。撤销权限后，不能只删除 token，而保留仍可返回旧结果的共享缓存。

**验证要求**：A/B 两用户同文写入、猜 hash 读取、跨分区删除、`store=all`、搜索与统计旁路、过期/撤销 grant，以及缓存和图关系的跨域访问。

### 3.8 本地化与隐私

**项目事实：如何实现**

默认 SQLite 路径和本地 embedding 使自托管本地运行可行；embedding 默认模型名为 `all-MiniLM-L6-v2`，有 ONNX 与 SentenceTransformer 路径，也有外部 OpenAI-compatible embedding adapter。[M14][M15][M27]

外部 embedding URL 一旦配置，会触发对应 API 调用；hybrid / Cloudflare 等配置可引入远端同步/推理。harvest 的可选 provider 链可接云服务或本地兼容服务；旧默认 provider 是 Groq，但无可用凭据不等于会成功调用。[M17][M27]

质量系统配置默认 local，但评价器在本地评分失败后还会检查配置可用的外部兼容服务/Groq 等路径。因此不能只看 `local` 单一开关就承诺零外发。Gemini 评分函数在本快照仍抛出 `NotImplementedError`，文档中的 provider 列表不能直接当成完成情况。[M16][M33]

**Vault 判断**

本地隐私路线成立，但必须把存储、embedding、分类/摘要、评分、同步和 Agent 本身分开审计。模型权重首次下载通常是下载行为；将正文送到外部 embedding/LLM 是内容外发，两者不能混为一谈。

推荐专用隔离运行环境，固定 `sqlite_vec`、禁用云同步及不需要的评分/LLM/自动处理，清理继承环境的云凭据，预置模型并限制出站。若 Agent 是云模型，它读取的记忆仍会离开本机，这与后端使用本地 embedding 无关。

**验证要求**：首次启动与缓存后断网运行分开测试；捕获 store、search、harvest、评分失败和后台任务的出站请求；对实际发布配置验证日志中不记录私密正文。不要承诺上游已经提供静态加密或端到端加密保险箱。

### 3.9 可改造性

**项目事实：如何实现**

存在清晰的扩展入口：DocumentLoader 注册新格式，MemoryStorage 抽象替换后端，MemoryService 聚合业务逻辑，Python entry_points 加载插件。插件支持 on_store、on_delete、on_retrieve、on_consolidate；on_retrieve 可修改结果。[M03][M18][M19][M26][M28]

但插件 registry 对 handler 异常采取记录日志后继续的方式，on_store 等也是副作用式回调；因此它不是事务性、失败即拒绝的授权机制。服务还涉及去重、演化、自动分块、多后端和同步，不能仅凭“有插件”就认为改造成本很低。[M18][M31]

**Vault 判断**

适合做薄适配而非把整个产品改造成 Vault。建议优先使用稳定服务边界，将候选、授权、证据、导出留在 Vault。插件可做非关键遥测或辅助关联；必须可靠的审计记录应在 Vault 事务/事件机制中完成，不能依赖可失败后继续的 hook。

如果要更换存储，不能只实现 store/search 两个函数，还需确认分块、过滤、图关系、版本、删除和同步需要的能力。避免为了 MVP 同时接入多个后端。

**验证要求**：完成一个最小 adapter，覆盖写入映射、限定 namespace 检索、删除和全量重建；人工触发插件异常，确认不会破坏 Vault 的审核与授权；升级一次小版本验证接口差异。

### 3.10 许可证风险

**项目事实：许可证是什么**

当前根 LICENSE 是 **Apache License 2.0**，包元数据同样声明 Apache-2.0，存在 NOTICE。[M01][M02][M29] 少数源码历史说明仍出现 MIT，但同一文件顶部已有 Apache 许可头；不能据旧注释将整个当前项目归类为 MIT。[M19]

Apache-2.0 允许商业利用和修改分发，在分发时要求提供许可证、保留适用声明、标注修改，并按规定保留 NOTICE；另有专利授权、专利诉讼终止与商标边界。[L01]

**Vault 判断**

相对 AGPL，它更适合许可尚未确定或闭源的 MVP 后端路线，但“宽松许可证”不是免除义务。应保留上游出处、提交、LICENSE/NOTICE 和修改说明，并核查发行包依赖、字体、模型权重及可选组件的独立许可。

本次结论只覆盖所查项目主许可证与可见说明；不代表每个依赖和模型均已审计完毕，也不代表对其全部历史代码权属作出保证。

**验证要求**：锁定实际交付版本，生成组件与模型清单，核对最终镜像/包中包含的第三方通知。主许可证核查通过后可进入技术 PoC，不应把旧 MIT 注释继续传播到选型材料。

## 四、Basic Memory：十维度深入核查

### 4.1 主流模型数据导入

**项目事实：如何实现**

1. **ChatGPT**：CLI `bm import chatgpt <conversations.json>` 读取 JSON，专用 importer 解析 conversation mapping，生成带标题、角色、消息时间的 Markdown 会话笔记。[B03][B05]
2. **Claude.ai**：有 conversations 与 projects 两类导入。会话 importer 使用 `chat_messages`，处理 sender、created_at、文本内容块，以及附件文件名和提取文本；projects importer 另处理项目资料。[B04][B06][B27]
3. **Markdown**：文件本身就是知识输入，放入项目并同步即可；不是必须经过聊天导入器。[B09][B12]
4. **JSON**：除了上述平台格式，另有特定 `memory.json` 实体/关系记录导入器。它按 entity、relation 等字段解释输入，不是任意 JSON 的通用语义理解器。[B07]
5. **ZIP**：本次 main 有项目 ZIP 规划模块，校验路径、展开大小、忽略规则并跳过嵌套归档。这是项目文件导入设施；ChatGPT/Claude 的 CLI 路径仍直接 `json.load`，不能将它写成已支持平台原始 ZIP 直接导入。[B05][B08][B27]
6. **Gemini**：本次专用导入器目录和 CLI 注册中未发现 Gemini/Takeout 历史适配器。能连接 Gemini 使用 MCP，与能导入 Gemini 历史无关。[B25]

**Vault 判断**

它是两者中更有价值的平台导入参考：可以研究字段解析、输出组织、时间缺失处理和错误统计。但“转成可读笔记”与“无损保留平台历史”不同。ChatGPT importer 深度遍历树，把替代分支输出到同一线性正文；只处理部分内容类型。文件名依赖日期和清理后的标题，不能取代稳定来源 ID。

Vault 应独立实现平台适配器，并在转换前保存全部原始字段与附件。若参考或复用其代码，必须同时处理 AGPL；不能把 AGPL 导入器复制到闭源模块后认为只借用了“小段流程”。

**验证要求**：同日同标题会话、重命名后重复导入、分支与重新生成、多模态、附件、缺时间以及中途失败恢复；同时验证未来平台格式改变时能报告未支持字段。

### 4.2 记忆存储

**项目事实：如何实现**

Basic Memory 的领域模型将 Markdown 作为 note 知识的规范表示；YAML frontmatter 表达标题、类型、permalink 和自定义 metadata，正文可有 observation 和 relation 语法。数据库维护 project、entity、observation、relation 与检索投影。[B09][B10][B12]

Entity 有内部数据库 ID、用于 API 的 external UUID、项目 ID、文件路径、permalink、checksum 和时间等。默认数据库是 SQLite；本地语义索引用 sqlite-vec，配置还支持 Postgres 与 pgvector/Milvus 的组合。[B10][B11]

当前源码也包含已接受内容、变更日志与文件物化等运行机制，因此“数据库只是索引”是领域上的知识主从关系，不应被解释成任何时刻删除 DB 都不会丢失操作历史或尚未落盘的状态。[B10][B18][B20]

**Vault 判断**

它的可读格式与 Vault 的用户掌控目标相容，但一个 note 不一定等于一条原子 memory：长笔记可能包含多个事实、多个来源及相互更新的观点。若用作后端，必须先决定是一条记忆一个 note，还是一个 note 中每条 observation 对应不同 Vault ID。

可将 Vault 核心记录渲染为带自定义 frontmatter 的 Markdown 投影，但 Vault 的 canonical schema、版本和证据仍由 Vault 定义。BM external_id 是其 API 身份，不是原平台 conversation/message ID；不能混用。

**验证要求**：frontmatter 扩展字段往返、移动/改名后的外部 ID、离线编辑同步、删除 DB 后知识及历史分别恢复到什么程度，以及写入成功到文件物化之间的故障恢复。

### 4.3 记忆形成

**项目事实：如何实现**

核心路径是人或 Agent 编写 Markdown，经解析产生结构化 observations / relations 并建立索引。解析“已写好的结构”不等于后台 LLM 自动从所有对话中发现真实事实。[B09][B12]

官方 memory-capture 技能指导 Agent 把当前会话状态综合成一个笔记；有稳定 thread ID 时写入 metadata 并更新同一笔记。memory-ingest 技能则指导从转录文本发现实体、关系与行动项，并要求对新实体先征得用户同意。这些是 Agent 的工作流程约定。[B13][B14]

当前 hook 实现还可从 Claude/Codex 等会话转录抽取开头请求和最近对话形成 pre-compaction 检查点，标记 `capture: extractive`；它刻意略过一些元帧和工具结果。它不是完整轨迹归档，也不是事实可信度判定。[B16]

**Vault 判断**

不能说 Basic Memory 完全没有自动捕获，也不能把外部 Agent 生成和文件解析视为经过验证的自动记忆抽取。技能中的“需要同意”是行为指引；存储 API 的合法写入并不自动要求一个不可伪造的用户审批凭据。

适合借鉴“可读的候选笔记 + 人类修改”体验。Vault 应强制分离模型提案、人工确认与生效；更新同一笔记不能覆盖历史证据，capture 的最终状态摘要也不能成为唯一事实来源。

**验证要求**：Agent 直接调用 write_note 是否绕过候选确认；修改前后能否定位已确认版本；技能不执行或模型违背提示时，服务端仍必须阻止未确认内容被授权检索。

### 4.4 来源可追溯性

**项目事实：如何实现**

笔记及其 observations/relations 可回到源 Markdown，entity 保存文件路径和 checksum；会话导入输出正文中有角色与时间。这提供了“知识来自哪个笔记/会话文本”的基础。[B03][B04][B10]

但 ChatGPT importer 的 frontmatter 不自动存 conversation ID，正文不输出消息 ID 或父子分支关系；Claude importer 也未将消息 UUID 写成稳定证据锚点。BM 的新 external UUID 是笔记/资源身份，不能补回这些平台 ID。小样本核查证实了上述格式化行为，不能据此推论已覆盖所有真实导出变体。[B03][B04]

同时，当前版本并非处处只有路径：raw document ingestion 定义稳定源快照、checksum、提取器/流水线、run note，并支持文档来源结构；hook envelope 保存来源 session、时间、事件与 raw 状态。这些是更丰富的 provenance 基础，但覆盖的是特定摄取/事件路径。[B15][B17][B30]

**Vault 判断**

“笔记可追踪”“特定文档可复核”“所有记忆都有逐消息证据链”应分开评价。尤其普通 note 中的 observation 可能是 Agent 综合结论，返回所属 Markdown 只能证明它写在那里，不能证明原始用户曾这样说过。

值得借鉴 raw-document 的源快照/run 身份及 trace 与 memory 分离思想；但 Vault 仍需统一的 evidence 对象，把聊天、附件、文档、手动输入都纳入同一可检验契约。用户确认也必须绑定具体记忆版本，不能只保存一个可被 Agent 改写的 `confirmed` 字段。

**验证要求**：分别审计平台导入、手写 note、capture、hook、raw-document 五种路径的来源字段完整率；验证重建索引、移动文件与重新导出后，证据锚点是否保持有效。

### 4.5 记忆导出

**项目事实：如何实现**

规范知识在 Markdown 文件内，文件可以直接复制/版本管理；MCP/API 可读取笔记。`build_context` 按 memory URL、图遍历深度、时间范围和分页构造上下文，支持 JSON 与 text 输出；compact 模式会省略正文/观察，不等于固定 token 预算。[B09][B19]

本次 main 还包含 `bm okf export DESTINATION --project PROJECT`，导出本地项目为 OKF v0.2 兼容静态目录：转换 WikiLinks，保留特定 frontmatter 和 BM 关系扩展，处理附件及日志。其手册明确云项目需先拉到本地、并发修改下会拒绝导出，并提示日志接受记录与实际文件物化存在时差。[B18][B28]

因此不能再简单声称它“没有正式导出能力”；也不能把 main 中实现直接当成所有 0.23.2 安装包的承诺。JSON 上下文响应也不是完整数据库、trace 和原始来源的统一备份。

**Vault 判断**

它有较强的可读迁移基础，OKF 可作为 Memory Pack 的互操作参考。但 OKF 的知识目录和 Vault 的带授权记忆包不是同一契约：仍需确认版本、证据引用、撤销状态、脱敏、包校验和导出清单。

不能把 build_context 的默认分页结果当“导出全库”；也不能认为复制 Markdown 会携带数据库中的全部操作历史。导出到新模型后，已经交付的明文不能被技术上远程收回，应将“撤销未来读取”和“撤回已交付副本”分开定义。

**验证要求**：建立最小项目，导出后核对元数据、实体/关系、附件、观察和日志；对未知扩展字段和未解析链接给出明确告警；测试完整分页和文件变动时的导出失败行为。

### 4.6 MCP / API / SDK

**项目事实：如何实现**

有 MCP server、FastAPI REST 与 CLI。当前公开 API 为 v2，项目通过 external UUID 路由；MCP 工具经 typed client 调用 API，再到 service/repository。源码提供笔记读写、搜索、上下文、项目和资源等工具。[B20][B22][B23]

MCP 中的 typed clients 与 Python package 内部 service 便于扩展，但本报告没有据此认定存在版本稳定、独立发布的通用公共 SDK。官方云 API key/OAuth 和本地进程内 ASGI 是不同运行路径。[B21]

**Vault 判断**

集成可行。若希望保留 BM 特有图遍历与 memory URL，应通过薄适配器把结果转换成 Vault Memory/Evidence 引用，同时明确 project 和 external UUID 的映射。

Gateway 不应让客户端自由选项目或透传全部 MCP 工具。长期产品化宜依赖明确定义的接口子集，不直接绑定内部 repository 或写底层 SQLite，避免升级和许可边界同时失控。

**验证要求**：v2 API 契约、项目 UUID 路由、错误码、MCP 输出格式、请求终止/重试以及异步写入后的读一致性；固定最终交付的源码提交或发布包后再生成接口清单。

### 4.7 权限与命名空间

**项目事实：如何实现**

project 是正式领域边界，entity、observation、relation、search record 都归属于 project；文件目录、project ID 和 project-scoped 唯一约束共同组织知识。[B09][B10]

本地 API 的项目依赖主要验证 project external UUID 对应对象是否存在，并提供项目上下文；这不是验证当前用户拥有该项目。MCP 可发现/解析配置项目和进行本地/云路由，不能将项目选择能力等同于访问控制。[B20][B21][B29]

官方云文档存在团队成员角色与项目协作权限，但云产品能力不能自动归给当前本地 OSS 部署，更不能据文档推断其全部托管服务实现都在公开仓库中。[D03]

**Vault 判断**

它比单纯标签更有明确的知识隔离结构，但不足以直接承担 Vault 的主体、授权范围、到期、撤销和审计模型。project 可以作为 Vault namespace 的后端映射，却不能让 Agent 只凭传入 project 名/UUID 获得权限。

服务端需要校验所有入口，包括跨项目链接解析、graph traversal、全局搜索和导出。官方领域模型也要求托管调用方对跨项目目标单独授权，这个责任必须由 Vault Gateway 落实。[B09]

**验证要求**：不同 project 同名笔记、跨项目链接、项目列表泄露、任意 UUID、跨项目 scoped search、以及改写 metadata/前缀绕过边界的情况。

### 4.8 本地化与隐私

**项目事实：如何实现**

本地知识为 Markdown，数据库默认 SQLite；语义 embedding provider 默认 FastEmbed，模型配置为 `bge-small-en-v1.5`，并支持 OpenAI/LiteLLM 等其他 provider。官方当前文档说明标准安装默认具有语义搜索，不能沿用“只有全文、没有向量”的旧印象。[B11][D02]

Logfire instrumentation 与发送开关在配置中默认 false。项目可以单独设置 local/cloud，存在强制本地路由选项；启用云项目、同步或外部 provider 后，数据路径随之变化。[B11][B21][B24]

核心 Markdown 解析和索引不要求云 LLM 生成摘要，但外部 Claude/ChatGPT 等 Agent 通过 MCP 读到内容后，内容会进入那个 Agent 的处理环境。[B12][B23]

**Vault 判断**

两者都能支持本地路线；Basic Memory 的文件可读性有利于用户审查，却不等于文件已经加密。默认英文 embedding 对中文、混合技术术语与个人偏好检索的适用性需要实测。

本地模式下应固定本地项目、embedding 与可选 reranker，关闭不需要的遥测/云路由，预置模型缓存，并检查 Agent 宿主本身的外发。安装时包含 OpenAI/LiteLLM 依赖不代表默认调用其云 API，不能仅凭依赖列表认定泄露。

**验证要求**：断网启动与查询；误设 cloud project 后是否被隐私配置阻止；外部 embedding/reranker 是否显式提示；日志、缓存、备份和导出文件的敏感数据保存范围。

### 4.9 可改造性

**项目事实：如何实现**

项目架构将 API、MCP、CLI 作为入口，组合根负责配置和依赖；importers、Markdown 处理、service、repository、runtime 协议分层。Importer 将文件写入委派给 FileService，便于不同运行环境替换存储行为。[B22][B25]

同时，实际系统已经涉及文件同步、接受变更、异步物化、全文/向量/图索引、云路由及多种 Agent 插件，不能把它当成一组无状态 Markdown 函数。其 Agent 插件/skills 不等于所有核心业务都有统一、稳定的第三方插件 API。[B10][B18][B21]

**Vault 判断**

结构总体清晰，适合研究和独立服务适配；直接 fork 改成 Vault 会引入持续同步上游、文件/DB 一致性和 AGPL 的复合成本。最有价值的借鉴点是平台 importer 的分离、Markdown 规范表示、可重建检索投影，以及来源 snapshot/run 模型。

若采用“Vault 自有主记录 + BM 文件投影”，要避免用户同时在两边修改导致双主冲突。应明确外部 Markdown 修改是新候选，还是受限的有效修改入口；不能默默覆盖已确认记忆。

**验证要求**：独立 adapter 原型、单向投影重建、外部编辑回流、两会话并发改写、checksum 冲突和损坏索引恢复。技术验证可使用上游未修改服务，但产品集成方案仍要与许可路线一并确定。

### 4.10 许可证风险

**项目事实：许可证是什么**

根 LICENSE 是 **GNU AGPL v3**，`pyproject.toml` 声明 **AGPL-3.0-or-later**。[B01][B02]

AGPL 不禁止商业使用。许可证第 13 节对修改后的程序与用户远程网络交互规定提供相应源码的要求；复制、修改和分发也有对应条件。不能把它夸大为“任何 REST 调用方都必须开源”，也不能把独立进程或 HTTP 边界视为自动豁免。[B02]

**Vault 判断**

应按集成方式决策：

- **阅读设计、独立实现兼容格式**：与复制其代码不是同一行为；仍应保存独立实现依据，核查引用材料和可复用资源的许可。
- **用户自行部署的上游服务，Vault 通过公共协议互操作**：可作为技术路线研究，具体是否构成组合/衍生、是否分发组件，需要结合交付方式判断。
- **复制 importer、嵌入 Python 包、修改服务后作为产品提供网络访问**：属于需要认真评估源码提供与许可兼容义务的路线，不能默认保持全部闭源。
- **获得另外适用的商业授权**：须以权利人实际提供的书面范围为准；本次未核实可购买的具体授权条款，不假设已有闭源授权。

对于闭源且希望几周内交付的 MVP，建议先避免直接复制/嵌入 BM 代码，保留兼容与独立研究路线。若产品决定 AGPL 兼容开源，则许可不再是同样的阻断条件，应重新比较其文件与图谱能力。

本节是基于许可证文本的工程风险判断，不是对特定产品法律性质的确定性意见；最终交付架构及依赖许可仍需核查。

## 五、选型落地：复用边界与十维验收

### 5.1 建议的 MVP 责任分配

以下是 **Vault 架构建议**，不是对上游已有功能的描述：

```text
ChatGPT / Claude / Gemini / Markdown / ZIP
                    │
                    ▼
Vault 导入器：安全解包、原始对象归档、平台字段保留
                    │
                    ▼
标准化 Message / Trace / Evidence
                    │
                    ▼
候选生成器（可插拔；规则或经授权的本地/云模型）
                    │
                    ▼
Vault：用户确认、稳定 ID、版本、状态、来源与事件
                    │
          ┌─────────┴─────────┐
          ▼                   ▼
可重建检索投影           Memory Pack 构建器
mcp-memory-service       版本、证据、脱敏、清单
或许可明确后的 BM             │
          │                   ▼
          ▼                新模型/Agent
Gateway：认证、授权、撤销检查、结果重校验、审计
          │
          ▼
      被授权的 Agent
```

关键约束：后端命中只返回候选 ID/得分；Gateway 根据 Vault 当前版本、状态和有效授权再决定正文是否可交付。这样后端索引更新延迟、软删除或旧缓存不会直接成为“撤销后仍然可读”的理由。过滤和分页设计应防止先截断再授权导致大量漏召回；小规模 MVP 可对每个授权域使用独立投影简化边界。

### 5.2 `vault-memory/1` 的概念映射

下表仅列需要保留的**语义**，不是正式 schema 字段定义，也不表示上游原生支持该格式。

| Vault 必需语义 | mcp-memory-service 可关联位置 | Basic Memory 可关联位置 | Vault 必须掌握的约束 |
|---|---|---|---|
| 稳定记忆身份与版本 | metadata + 独立 hash/分块对照 | 自定义 frontmatter + entity external UUID 对照 | Vault ID 独立生成；内容变化和重建不改变逻辑身份 |
| 记忆正文与类型 | content / memory_type | note 正文 / observation / type | 定义原子粒度；不要把整篇会话自动视为已确认事实 |
| 来源证据 | 自定义 metadata 中的 Vault evidence 引用 | 自定义 metadata、关系或文档源引用 | 引用可校验的原始对象及消息，不依赖可变路径 |
| 候选、确认、撤销、替代 | 可做投影标签/metadata | 可做投影 frontmatter | 状态及审批事件在 Vault 强制校验，Agent 不可自行升级 |
| namespace 与授权 | store/独立实例作为组织映射 | project 作为组织映射 | 权限由有效 grant 决定，不信任客户端自报分区 |
| 导出与删除 | JSON 读取/导出、删除接口 | Markdown/OKF/上下文、文件/API 删除 | 统一导出清单和删除传播；缓存、备份策略单独定义 |

### 5.3 十维度 PoC 验收清单

以下为**建议验收项，尚未执行**。不以主观评分或虚构工作量替代验证。

| 对应维度 | 必须验证的输入/操作 | 通过条件 |
|---|---|---|
| 1. 导入 | ChatGPT 有分支、Claude 有附件、Gemini 样本、Markdown、自定义 JSON、ZIP | 原始文件完整保存；支持与未支持明确；消息 ID/时间/分支不被静默丢弃；重复导入幂等 |
| 2. 存储 | 同文不同用户/来源、版本改写、后端库重建 | 不跨用户合并；Vault 身份和来源不变；投影可恢复 |
| 3. 形成 | 中文/英文、否定、更正、冲突、临时事实 | 候选不可自动生效；用户确认绑定具体内容版本；抽取错误可拒绝和追踪 |
| 4. 溯源 | 任取记忆回放来源、修改原路径、导出重建 | 可定位原始消息和片段并验 hash；来源不可用时明确标记，不伪造证据 |
| 5. 导出 | 全量、分页、筛选、脱敏、二次导入 | 数量/ID/版本/来源一致；未知扩展不静默丢弃；无未授权记忆混入 |
| 6. 接口 | 选定 MCP/REST 子集、超时、重试、大结果 | 契约固定；重试无额外写入；截断明确；错误可恢复 |
| 7. 权限 | A/B 用户、跨 namespace、猜 ID、图遍历、撤销与缓存 | 任意入口均无法越权；撤销后的新读取被拒绝；审计可关联主体和返回记录 |
| 8. 隐私 | 冷启动、缓存后断网、评分故障、云凭据误配置 | 本地模式可工作；未经许可不外发正文；外发被阻断或明确记录 |
| 9. 改造 | 最小 adapter、上游升级、并发更新、hook 异常 | 可替换后端；不破坏主记录；失效 hook 不绕过权限；冲突有明确结果 |
| 10. 许可 | 最终发行包/镜像、模型、插件和修改清单 | 许可与产品分发模式匹配；提供所需通知/源码；未解决的许可条件不进入集成交付 |

### 5.4 决策规则

若目标是**尽快验证闭源/许可未定 MVP 的导入→确认→授权检索→迁移闭环**：先用 mcp-memory-service 的 SQLite 本地模式做可替换投影，关闭不需要的自动改写与云路径；平台导入与证据层由 Vault 自建。

若目标是**优先验证 Markdown 知识资产、图谱上下文与跨工具可读性**，且能够满足 AGPL 或明确获得其他适用授权：Basic Memory 值得并行作为备选方案做同一套十维验收；不要只凭许可证将其技术能力排除，也不要只凭文件可读性忽略证据和权限缺口。

如候选确认、来源回放、跨用户隔离、撤销后读取或本地隐私任一关键门槛未通过，仍可参考其接口与格式，但不应把该上游服务直接认定为 MEMO Vault 的产品基础。

## 六、已执行核查与未决事项

### 6.1 已执行的五项隔离小样本核查

使用从官方快照 AST 提取、保持方法体不变的格式化方法；替换了实体容器和时间格式化依赖。它用于检查转换语义，不是整应用集成测试：

1. ChatGPT 测试树含两个替代助手分支，Basic Memory 输出正文同时包含两条，未保留显式分支结构。
2. 测试 ChatGPT 的原 conversation ID/message ID 未进入该 formatter 生成的 frontmatter/正文。
3. 对测试用 `multimodal_text` 消息，ChatGPT `_get_message_content()` 返回空文本。
4. Claude formatter 保留测试文本，但不序列化该消息 UUID。
5. mcp-memory-service JSONLoader 将测试 mapping 中的 ID 和正文展开成带键路径的文本，未生成规范消息对象。

五项断言均通过。输入为自制合成样本，不包含用户真实聊天；结果与边界记录在 `research/import-probe-results.json`。这些结果支持本报告关于“有损导入”和“通用 JSON 不等于平台语义解析”的具体判断，不证明所有平台导出均兼容或均失败。

### 6.2 仍需明确的项目条件

- 提供正式 `vault-memory/1` schema 后，才能验证字段级无损映射与标准兼容。
- 明确 Vault 的单用户本地版/多用户服务边界、开源或闭源策略；这直接改变隔离方案与 AGPL 权重。
- 用实际目标语言、记忆类型、附件与工具轨迹建立质量样本；本报告没有宣称哪个项目召回率更高。
- 锁定发布版本验证 main 中新增的 store、OKF、文档摄取等功能是否进入目标包；不能只按源码版本字符串安装后假定一致。
- 最终部署再做依赖/模型许可清单、实际配置的出站检查和完整端到端验收。
